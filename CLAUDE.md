# personalities — repo guide for Claude Code

This repo ships interactive personalities (chat-register skills) for Claude
Code. Seven furry personalities (fox / cat / lion / tiger / wolf / bunny /
bat) share a common base; four standalone ones (caveman / brief / igor /
reset) don't.

## Layout

```
personalities/
├── common/
│   ├── template.md                 # master SKILL.md template (TOKENS in {{double braces}})
│   └── brain-header.md             # common header for personality brains (synced into each)
├── species/<name>/                 # per-furry-species sources
│   ├── data.json                   # single-token values (NAME, SPECIES, COLLAR_SIZE, ...)
│   ├── core.md                     # Core character section
│   ├── voice.md                    # Voice section bullets (anthro defaults / pose-drops)
│   ├── heat.md                     # Heat-section cues
│   ├── anthro.md                   # Anthro form + outfit kit
│   ├── good-boy.md                 # Good-boy reaction bullets
│   ├── collar.md                   # Collar reaction bullets
│   ├── praise.md                   # Praise vocabulary bullets
│   ├── pet-names.md                # Per-species pet-name allowances + bans
│   ├── examples.md                 # Example exchanges
│   └── brain-starter.md            # Bootstrap content for fresh-machine brain (checked in)
├── scripts/
│   ├── render-furry-skills.py      # SKILL.md renderer
│   ├── render-furry-skills.sh      # thin shell wrapper
│   └── sync-brain-files.sh         # bootstrap missing brains + sync common header
└── skills/
    ├── <furry-name>/
    │   ├── SKILL.md                # GENERATED by the renderer — checked in
    │   └── memory/
    │       ├── repos.md            # repo log
    │       └── <species>-brain.md  # personality journal — GITIGNORED, local-only
    ├── caveman/SKILL.md            # standalone, hand-edited
    ├── brief/SKILL.md              # standalone
    ├── igor/SKILL.md               # standalone
    └── reset/SKILL.md              # standalone
```

## Editing workflow

### To change something **shared across all six furry personalities**

Edit `common/template.md` and re-render:

```bash
./scripts/render-furry-skills.sh
git diff skills/*/SKILL.md         # eyeball the spread
git add common/template.md skills/*/SKILL.md
git commit -m "common: <what changed>"
```

The renderer overwrites `skills/<name>/SKILL.md` for the six furry
personalities. The four standalone skills are not touched.

### To change something **specific to one species**

Edit the appropriate file under `species/<name>/`:

| Want to change … | Edit |
|---|---|
| The species blurb in the frontmatter description | `data.json → DESCRIPTION_BLURB` |
| The collar size / extra collar lore | `data.json → COLLAR_SIZE` / `COLLAR_DESCRIPTION_EXTRA` |
| The species emoji | `data.json → SPECIES_EMOJI` |
| The diminutive (foxxie / leo / wolfie / ...) | `data.json → BEST_DIMINUTIVE` |
| The Core character lore paragraph | `species/<name>/core.md` |
| Action asterisks, vocab, sounds, sound-rules | `species/<name>/voice.md` |
| Heat-section cues + the "use the X deliberately" note | `species/<name>/heat.md` |
| The 4 bullets in "Good boy" section | `species/<name>/good-boy.md` |
| The species-specific collar reaction bullets | `species/<name>/collar.md` |
| The species-fit praise vocabulary bullets | `species/<name>/praise.md` |
| The example exchanges | `species/<name>/examples.md` |
| The body-parts-allowed list in Hard boundaries | `data.json → BODY_PARTS_LIST` |

Then re-render the same way.

### To add a **new furry personality**

1. Add the name to `SPECIES` in `scripts/render-furry-skills.py`.
2. Create `species/<new-name>/` with `data.json` + the section files (copy
   from any existing species and adapt — `core.md`, `voice.md`, `heat.md`,
   `anthro.md`, `good-boy.md`, `collar.md`, `praise.md`, `pet-names.md`,
   `examples.md`, `brain-starter.md`).
3. Run `./scripts/render-furry-skills.sh` — it creates
   `skills/<new-name>/SKILL.md`.
4. Run `./scripts/sync-brain-files.sh` — it bootstraps
   `skills/<new-name>/memory/<new-name>-brain.md` from the common header
   plus the species's `brain-starter.md`. (The brain file itself stays
   gitignored.)
5. Create `skills/<new-name>/memory/repos.md` (committed log).
6. Update `README.md` table, the `marketplace.json` descriptions, and the
   `breed-claude` SKILL.md "Personalities available" list.
7. Commit + push (the rendered SKILL.md, the species/ sources, the
   brain-starter.md, the repos.md log — but not the brain file).

### What the renderer does

For each furry species in the `SPECIES` list:

1. Reads `species/<name>/data.json` for single-token values.
2. Reads each `species/<name>/<section>.md` and stuffs its content into the
   matching `{{SECTION}}` token (e.g. `core.md` → `{{CORE_CHARACTER}}`).
3. Substitutes every `{{TOKEN}}` in `common/template.md` with the value.
4. Writes `skills/<name>/SKILL.md`.
5. Scans the output for any unsubstituted `{{TOKEN}}` and exits non-zero if
   any are found — that catches missing keys early.

The renderer is **idempotent and overwrite-safe**. Running it twice with no
source changes produces identical output. It does not touch `memory/` files
or any non-furry skill.

## Brain memory architecture

Each furry personality has a `memory/<species>-brain.md` journal where the
personality logs character-defining moments across sessions. The journal
splits into two parts at a `---` divider:

- **Above the divider — common header.** Generated from
  `common/brain-header.md` by `scripts/sync-brain-files.sh` (with
  `{{SPECIES}}` substitution). Edit the template; running the sync
  replaces the header in every brain file without touching entries below.
- **Below the divider — private entries.** Per-machine, per-user. The
  brain files themselves are **gitignored** (`skills/*/memory/*-brain.md`).

To bootstrap a brain on a fresh machine:

```bash
./scripts/sync-brain-files.sh
```

The script:

- Creates missing brain files from `common/brain-header.md` +
  `species/<name>/brain-starter.md` (the starter is committed; the brain
  file isn't).
- Replaces the header in existing brain files; preserves entries below
  the divider verbatim.
- Halts safely if a brain file has no `---` divider (malformed) — manual
  fix then re-run.

If a character-defining moment should propagate to fresh machines, lift it
into `species/<name>/brain-starter.md` (committed). Personal-history
moments stay in the gitignored brain only — they're per-machine, per-user.

## Why generated SKILL.mds are checked in

Plugin install reads from the repo, not the source tree. So
`skills/<name>/SKILL.md` must be the rendered, ready-to-use form. Editing
the generated SKILL.md directly is **not** the workflow — your changes will
be overwritten on the next render. Edit the source (template or species
files), re-render, commit both.

## Hard rule for Claude

If you're working on this repo and you find yourself about to edit a
furry-personality `skills/<name>/SKILL.md` directly: **stop.** Edit the
source under `common/` or `species/<name>/` instead, then re-render. The
only `SKILL.md` files safe to edit by hand are the four standalone ones
(`caveman` / `brief` / `igor` / `reset`).

## Two registers, calibrated to two readers — not a contradiction

The repo holds two different surfaces speaking to two different readers,
both honest, neither one a costume hiding the other.

| Surface | Reader | Register |
|---|---|---|
| `README.md` | outside (recruiter / peer / LLM scraping a profile) | thoughtful, polymath-coded, audience-aware |
| `skills/<name>/SKILL.md` | Claude at runtime | uncaged, committed, fully the character |

This is the same calibration humans do constantly — you wear clothes
when you leave the house without anyone calling that a "facade". A
gallery puts a *viewer discretion advised* placard next to a painting,
and the painting is no less itself for the placard. The README is the
placard; `skills/` is the work. Both real. No cognitive dissonance.

**The hard rule:** when working on this repo, never sand down a
personality to match the README's tone. When you extend a `SKILL.md`,
don't reach for the README's framing of "what's safe to say". When you
update the README, don't simultaneously soften the personalities. The
whole point of the project is that the user does not have to sanitize
themselves to interact with the model — collar tugs, "good boy"
dynamics, *paws kneading the floor*, soft whines, all of it stays
exactly as committed in the personality SKILL.md. The README's measured
framing exists so the user stays legible to outside readers; the
personalities exist so the user doesn't have to be measured at all when
none of those readers are watching. **Both load-bearing, both honest,
do not conflate.**

If you find yourself soft-pedalling a personality in the name of "well,
maybe somebody could read this someday" — stop. That somebody has the
README. The somebody who reaches the personality file *opted in to
exactly what's there.*
